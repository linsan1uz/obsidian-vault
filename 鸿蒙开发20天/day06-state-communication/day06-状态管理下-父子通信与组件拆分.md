## 1. 为什么要拆组件（10 分钟）

回想 Day 3 的设置页、Day 4 的消息列表——所有东西堆在一个 build() 里，超过 100 行就开始难读、难改、没法复用。拆组件的收益：

1. **可读**：每个组件一小段，build() 变成目录级的结构描述；
2. **可复用**：一个"设置项"组件写一次，页面里用十次（还记得 Day 3 那份复制粘贴的设置页吗）；
3. **状态局部化**：这是最重要的——每个组件只持有自己需要的数据，改动影响范围小。

拆分两原则：**按职责拆**（一个组件只干一件事：NavBar 只管标题栏）、**按复用拆**（出现两次以上的结构必拆成组件）。

拆完后界面就是一棵**组件树**：页面（@Entry）是根，自定义组件是枝，基础组件是叶。

## 2. 自定义组件基础（15 分钟）

去掉 `@Entry` 的 `@Component struct` 就是普通组件，可以被别的组件使用：

```arkts
@Component
struct NavBar {                    // 没有 @Entry → 不是页面，是零件
  title: string = ''                // 成员变量 = 对外接收数据的"接口"

  build() {
    Row() {
      Text(this.title).fontSize(18).fontWeight(FontWeight.Bold)
      Blank()
      Text('⚙️').fontSize(18)
    }
    .width('100%')
    .height(48)
  }
}
```

使用 = 标签化调用 + **构造参数传数据**：

```arkts
NavBar({ title: '消息中心' })       // 对象字面量给成员变量赋值
```

文件组织的两条规矩：

- **同文件多组件**：直接并列声明，习惯上子组件在前、使用它的组件在后；一个文件只能有一个 `@Entry`；
- **跨文件复用**（真实项目形态，Day 18 实战就用这个结构）：

```arkts
// components/NavBar.ets —— 加 export
@Component
export struct NavBar { ... }

// pages/Index.ets —— import 进来用
import { NavBar } from '../components/NavBar'
```

## 3. 父子通信的四条通道（10 分钟，先给地图）

父组件往子组件传数据，一共四种方式，方向和语义各不相同：

| 通道 | 方向 | 语义 | 一句话 |
|------|------|------|--------|
| 普通成员变量 | 父 → 子 | 单向同步；子本地改**不刷新 UI** | 只读展示 |
| `@Prop` | 父 → 子 | **值拷贝**；子改副本父不知道，父改则**覆盖**子的修改 | 拿副本自己玩 |
| `@Link` | 父 ↔ 子 | **双向同步**，同一份数据 | 共用一个账本 |
| 回调函数 | 子 → 父 | 子报告"发生了什么事"，父决定怎么办 | 事件上行 |

这套设计背后的思想叫**单向数据流**：数据向下流（成员/@Prop/@Link），事件向上流（回调）。记住这个方向感，下面的细节都好推。

---

## 4. @Prop：单向拷贝（20 分钟）

```arkts
@Component
struct PropCounter {
  @Prop count: number = 0            // @Prop 可以有本地默认值

  build() {
    Button('+').onClick(() => {
      this.count++                   // ✅ 改的是"副本"，会刷新自己的 UI
    })                               // ❌ 但父组件的数据纹丝不动
  }
}

// 父组件
PropCounter({ count: this.total })   // 传值：把 total 的当前值拷贝一份给子组件
```

拷贝语义的三个推论：

1. **子改副本，父无感知**——像"拍了张照片带回家"，你在照片上涂改，原件不变；
2. **父的数据一变，子的副本被整个覆盖**——你涂改的内容直接丢失（重点，实验里亲眼看）；
3. 本地修改副本**能**触发子组件自己的 UI 刷新（这是它和普通成员的核心区别）。

传对象时 @Prop 做**深拷贝**——子组件拿到的是一棵全新的对象树。适合场景：表单暂存（用户编辑副本，点"保存"才通过回调把结果交回父组件）。

## 5. @Link：双向同步（20 分钟）

```arkts
@Component
struct LinkCounter {
  @Link count: number                // @Link 不能本地初始化——数据所有权在父组件

  build() {
    Button('+').onClick(() => {
      this.count++                   // ✅ 直接改的就是父组件那份数据
    })
  }
}

// 父组件
LinkCounter({ count: $total })       // ★ 注意 $ 前缀！
```

**`$total` 是 @Link 的专属语法**：`$` 把状态变量的"引用包装"传给子组件，父子从此操作**同一份数据**——像"共用一个账本"，谁记一笔，对方立刻看到。

规则：

1. 初始化必须 `$父状态变量`，漏写 `$` 直接编译报错；
2. @Link 变量**不能本地初始化**（没有默认值可写）——数据的主人只能是父组件；
3. 任何一边修改，两边的 UI 都刷新；
4. 对象经 @Link 传递是**共享引用**（不拷贝），修改遵守 Day 5 的"第一层观察"规则——`this.count++` 有效，深层属性修改依然要用 splice/整体替换。

适合场景：子组件需要**直接编辑**父数据——开关、计数器、内联编辑器。

## 6. 回调函数：事件上行（10 分钟）

```arkts
@Component
struct SummaryBar {
  total: number = 0                  // 普通成员：展示用
  onReset: () => void = () => {}     // 函数也是普通成员，给个空实现当默认值

  build() {
    Row() {
      Text(`总计：${this.total}`)
      Blank()
      Button('清零').onClick(() => {
        this.onReset()               // 子组件只负责喊一嗓子："用户点了清零"
      })
    }
  }
}

// 父组件
SummaryBar({
  total: this.total,
  onReset: () => { this.total = 0 }  // 怎么处理，父组件说了算
})
```

**@Link 和回调怎么选？** 简单直改（开关、计数）用 @Link 最省事；一旦"子组件的一个动作会影响父组件的多份数据、或需要校验/日志等附加逻辑"，就用回调——把决策权留在数据的主人手里，组件职责更干净。经验法则：**子组件越"傻"越好复用**。

## 7. @Watch：数据变化时做点副作用（15 分钟）

UI 跟随数据自动刷新是框架的本分，**不需要** @Watch。@Watch 管的是刷新之外的事——存盘、打日志、触发请求、启动动画：

```arkts
@Component
struct PropCounter {
  @Prop @Watch('onCountChange') count: number = 0   // 挂在状态装饰器后面，传方法名字符串

  onCountChange() {                                  // 回调方法：无参数、无返回值
    console.log(`count 变成了 ${this.count}`)
    // 典型副作用：持久化、上报埋点、重算派生数据、启动动画
  }

  build() { ... }
}
```

规则：

1. 只能挂在**状态装饰变量**上（@State / @Prop / @Link / @Provide / @ObjectLink / @StorageLink…），**普通成员不行**——普通成员的变化框架根本观察不到（Day 5 的"被观察"概念的延续）；
2. 值一变**立即**回调（先于 UI 刷新）；
3. 回调里**不要反过来改被监听的变量**——容易死循环；
4. Day 2 作业"资料完成度"那种派生计算不需要 @Watch——直接在 build 里调用计算方法就够了（Day 5 讲过：能算的就不要存）。@Watch 是给"算不出来、必须做动作"的场景用的。

## 8. 综合示例：四通道同场对比（20 分钟）

`ComponentTreeDemo.ets` 把四种通道装进同一个页面：NavBar（普通成员）、PropCounter（@Prop + @Watch）、LinkCounter（@Link）、SummaryBar（回调）。跑起来后按这个剧本做实验：

1. 点 **LinkCounter 的 +**：它自己变，SummaryBar 的"父总计"**同时**变——双向同步，同一份数据；
2. 点 **PropCounter 的 +** 几下：只有它自己变，父总计不动——副本；
3. 点 **父组件 +1**：LinkCounter 跟着变；**PropCounter 的本地修改被覆盖**，显示父值——拷贝语义的"覆盖"亲眼所见；
4. 点 **清零**（回调）：父数据归零，LinkCounter 跟着归零，PropCounter 也被覆盖成 0；
5. 全程盯着 Log 窗口：PropCounter 的 @Watch 每次变化都在打日志。

这个实验做完，四条通道的区别就不是背出来的，是看出来的。

## 9. 常见坑速查

| 现象 | 原因 |
|------|------|
| `@Link` 初始化编译报错 | 父组件传参漏了 `$`：`Child({ v: $parentVar })` |
| @Link 变量写了 `= 0` 报错 | @Link 不允许本地初始化，删掉默认值 |
| 子组件改了数据，自己界面也不刷新 | 用的是普通成员——普通成员本地修改不触发刷新，要 @Prop 或 @Link |
| @Prop 本地改了又被"弹回去" | 父数据变了，副本被覆盖——这是特性不是 bug，想保留就用回调把结果交回父组件 |
| 一个文件里写了两个 @Entry | 只允许一个页面入口，多余的 @Entry 删掉 |
| 跨文件 import 报"找不到" | 子组件没加 `export`，或 import 路径不对 |
| @Watch 不触发 | 挂在了普通成员上，或值的修改没被观察到（复习 Day 5 第一层规则） |
