> **今日目标**：把大页面拆成组件树；掌握父子组件传数据与传事件的四种方式（普通成员 / @Prop / @Link / 回调）；学会用 @Watch 在数据变化时执行副作用。

> **配套代码**：`MusicPlayerDemo-5.3.ets`（音乐播放页，本课全程围绕它展开）

## 1. 组件化：从"一整页"到"一棵树"（15 分钟）

前五天写的都是"一个 struct 装下一个页面"。页面一大，问题就来了：

- build() 上百行，找一个按钮要滚半天；
- 同样的结构出现两次以上，改样式就得改多处；
- 所有 @State 挤在一个组件里，谁改了什么一目不了然。

解法是**拆组件**：把界面切成一个个职责单一的 `@Component struct`，页面变成组件树的根。

```arkts
// 没有修饰 @Entry 的 struct 就是"零件"，不能单独成为页面
@Component
struct PlayButton {
  playing: boolean = false          // 成员变量 = 这个零件的"插口"

  build() {
    Button(this.playing ? '⏸ 暂停' : '▶ 播放')
      .width(120)
      .height(120)
      .type(ButtonType.Circle)
      .fontSize(40)
  }
}
```

使用时标签化调用，用**对象字面量**给成员赋值：

```arkts
PlayButton({ playing: this.isPlaying })
```

### 什么时候拆？

| 信号 | 动作 |
|------|------|
| 同样的 UI 结构出现 ≥ 2 次 | 必拆 |
| 一块 UI 有独立职责（标题栏、播放控制区、进度区） | 建议拆 |
| 只是几行摆在一起的一次性排版 | 不拆，过度拆分反而难读 |

### 文件组织

- **同文件**：多个 @Component 并列声明即可，一个文件最多一个 @Entry；
- **跨文件**（正式项目形态）：

```arkts
// components/PlayButton.ets
@Component
export struct PlayButton { ... }

// pages/Index.ets
import { PlayButton } from '../components/PlayButton'
```

建议目录：`pages/` 放页面、`components/` 放零件——Day 18 实战项目沿用这个结构。

## 2. 拆完之后，第一道坎：数据怎么传（10 分钟）

组件拆开，数据却是一体的：播放按钮要读"是否在播放"，音量滑块要改"音量"——这些数据在父组件（页面）手里，子组件怎么拿、怎么改？

ArkUI 的答案是**单向数据流**：

```
        数据向下流（父 → 子）
   ┌──────────────────────────┐
   │  页面（@State，数据的主人） │
   └──────────────────────────┘
     ↓ 传值          ↓ 传引用      ↑ 事件
  展示型子组件    编辑型子组件   ────────┘
        （子 → 父）
```

落到语法上是四个工具，先看地图再逐个拆：

| 工具 | 方向 | 本质 | 口诀 |
|------|------|------|------|
| 普通成员 | 父 → 子 | 传值，只做展示 | 只是看看 |
| `@Prop` | 父 → 子 | 传**拷贝**，子改不影响父 | 自己改着玩 |
| `@Link` | 父 ↔ 子 | 传**引用**，父子同一份数据 | 一起改 |
| 回调函数 | 子 → 父 | 子报告事件，父执行逻辑 | 按门铃 |

## 3. 普通成员：只是看看（15 分钟）

```arkts
@Component
struct SongInfo {
  title: string = ''        // 父传什么显示什么
  artist: string = ''

  build() {
    Column({ space: 4 }) {
      Text(this.title).fontSize(20).fontWeight(FontWeight.Bold)
      Text(this.artist).fontSize(14).fontColor('#999999')
    }
  }
}

// 页面里
SongInfo({ title: '晴天', artist: '周杰伦' })
```

规则只有两条：

1. 父组件数据变化时，子组件**会**跟着更新（单向同步）；
2. 子组件自己改它，**不会**触发 UI 刷新（框架不观察它——Day 5 讲过的"被观察"概念，普通成员不在观察范围内）。

所以口诀是"只是看看"：**子组件只读不写**的数据，一律用普通成员，别加装饰器。装饰器不是越多越好，每个状态装饰变量都有观察成本。

## 4. @Prop：自己改着玩（20 分钟）

子组件有时候需要**改一改**传进来的值，但不该惊动父组件——比如"编辑中的昵称草稿"、"本地预览用的缩放比例"。这时用 @Prop：

```arkts
@Component
struct RatingStars {
  @Prop rating: number = 0          // 可以有本地默认值

  build() {
    Row({ space: 4 }) {
      Text('★'.repeat(this.rating)).fontSize(22).fontColor('#FFB800')
      Text('☆'.repeat(5 - this.rating)).fontSize(22).fontColor('#CCCCCC')
    }
    .onClick(() => {
      this.rating = this.rating >= 5 ? 0 : this.rating + 1   // ✅ 改副本，自己的 UI 立刻刷新
    })
  }
}

// 页面里：传的是值
RatingStars({ rating: this.initRating })
```

**@Prop 是拷贝**，三个特性都从这一点推出来：

1. 子组件改的是副本，父组件的 @State 纹丝不动；
2. 本地修改能触发**子组件自己**的 UI 刷新（和普通成员的区别）；
3. 父数据一变，副本被**新值整体覆盖**——你本地改的东西会被冲掉。

第三条最重要，想清楚再用：@Prop 适合**草稿态**（改完通过回调把结果交回父组件），不适合"父子要同步"的场景——那是 @Link 的工作。

传对象时 @Prop 做深拷贝（子组件拿到一棵全新的对象树），天然隔离，草稿不会污染源数据。

## 5. @Link：一起改（20 分钟）

音量滑块拖一下，页面上的音量数字、静音按钮状态都要变——子组件要改的就是"父组件那份数据本身"。@Link 传的是**引用**：

```arkts
@Component
struct VolumePanel {
  @Link volume: number              // ★ 不能写本地默认值

  build() {
    Column({ space: 8 }) {
      Text(`音量 ${this.volume}%`).fontSize(14)
      Slider({ value: this.volume, min: 0, max: 100 })
        .onChange((v: number) => {
          this.volume = Math.round(v)    // 直接改父组件的数据
        })
    }
  }
}

// 页面里：传的是引用，注意 $ 前缀
VolumePanel({ volume: $thisVolume })
```

两条硬规则：

1. **初始化必须用 `$`**：`$volume` 是"状态变量的引用"语法，漏写直接编译报错；
2. **@Link 变量禁止本地初始化**——数据的所有权在父组件，子组件没有资格给默认值。

行为特征：任何一边修改，两边的 UI **同时**刷新，因为它们本来就是同一份数据。对象经 @Link 是共享引用，修改生效范围遵守 Day 5 的第一层观察规则。

@Prop 和 @Link 一张表看清：

| | @Prop | @Link |
|---|-------|-------|
| 传的是什么 | 值的拷贝 | 引用 |
| 子改影响父吗 | 否 | 是 |
| 父改覆盖子吗 | 是（冲掉本地修改） | 无"覆盖"概念，本来就是一份数据 |
| 本地默认值 | 可以 | 不允许 |
| 初始化语法 | `{ v: this.x }` | `{ v: $x }` |
| 典型场景 | 草稿、本地预览 | 计数器、开关、滑块 |

## 6. 回调：按门铃（15 分钟）

第四条通道方向反过来：子组件不碰数据，只报告"**发生了一件事**"，处理权完全在父组件：

```arkts
@Component
struct ControlBar {
  playing: boolean = false
  onToggle: () => void = () => {}     // 函数成员，默认空实现兜底
  onNext: () => void = () => {}

  build() {
    Row({ space: 24 }) {
      Button(this.playing ? '⏸' : '▶')
        .onClick(() => this.onToggle())     // 只按门铃
      Button('⏭')
        .onClick(() => this.onNext())
    }
  }
}

// 页面里：怎么响应，页面说了算
ControlBar({
  playing: this.isPlaying,
  onToggle: () => {
    this.isPlaying = !this.isPlaying          // 逻辑在父
    console.log(`播放状态：${this.isPlaying}`)
  },
  onNext: () => { this.playNext() }
})
```

**@Link 和回调怎么选？** 问自己"这个动作是简单直改，还是一个决策"：

- 拖滑块改音量——**直改**，@Link；
- 点播放键——牵扯播放器状态、请求、日志，是**决策**，回调。

用回调时子组件不需要理解业务，只负责"喊一声"，所以**子组件越笨，复用性越强**——ControlBar 明天就能搬到别的播放器里用。

## 7. @Watch：数据变了，顺手做点事（15 分钟）

UI 跟着数据刷新是框架自动的，用不着 @Watch。@Watch 解决的是"刷新之外"的动作——**副作用**：

```arkts
@Entry
@Component
struct MusicPlayer {
  @State @Watch('onVolumeChanged') volume: number = 40

  onVolumeChanged() {                    // 无参无返回值，值一变立即调用
    console.log(`[持久化] 音量=${this.volume}`)   // 存盘、埋点、开动画、发请求……
  }
}
```

规则四条：

1. 语法 `@State @Watch('方法名')`，也适用于 @Prop / @Link 等状态装饰变量；**普通成员挂不了**（它的变化框架看不见）；
2. 回调触发时机：值变化后立即执行；
3. 回调里不要反过来修改被监听的变量——容易无限套娃；
4. **派生数据不需要 @Watch**。合计、完成度这类"算出来的值"，直接在 build 里调用方法，每次刷新自动重算（Day 5 的"能算不存"）。

一句话定位：**@Watch 是数据的"事件监听器"，不是刷新工具**。

## 8. 综合案例：音乐播放页（30 分钟）

完整代码在 `MusicPlayerDemo-5.3.ets`，组件树：

```
MusicPlayer（页面，全部 @State 的主人）
├── SongInfo          普通成员（title/artist）      —— 只是看看
├── VolumePanel       @Link（volume）+ @Watch       —— 一起改
├── RatingStars       @Prop（rating 草稿）+ 回调确认 —— 自己改着玩
└── ControlBar        普通成员（playing）+ 回调      —— 按门铃
```

一个组件一条通道，每种通信方式各就各位。跑起来按这个清单验证：

1. **拖音量滑块**：滑块、音量数字同步变（@Link 同一份数据），Log 窗口每拖一次输出一行持久化日志（@Watch）；
2. **点星级**：星星先自己变（@Prop 本地副本）；点"提交评分"才通过回调把结果交回页面（草稿态的完整闭环）；
3. **点播放/下一首**：按钮状态由页面数据驱动（普通成员单向同步），逻辑全部在页面的回调里执行；
4. 想看 @Prop 被覆盖的效果：点星级改成本地 5 星后，再点页面上的"重置评分"——本地草稿被父值冲掉。

## 9. 常见坑速查

| 现象 | 原因 |
|------|------|
| @Link 初始化编译报错 | 漏了 `$`：`VolumePanel({ volume: $thisVolume })` |
| @Link 写 `= 0` 报错 | @Link 禁止本地初始化 |
| 子组件改数据，界面没反应 | 改的是普通成员，本地修改不触发刷新 |
| @Prop 的本地修改莫名消失 | 父数据变化把副本覆盖了——特性不是 bug |
| 所有成员都挂上装饰器"保险" | 展示型数据用普通成员，装饰器有观察成本 |
| @Watch 不触发 | 挂在普通成员上；或修改方式没被观察（Day 5 第一层规则） |
| 同文件写两个 @Entry | 一个文件只允许一个页面入口 |
| import 组件报找不到 | 子组件没 export，或路径写错 |
